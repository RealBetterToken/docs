## Short answer

`model_provider` tells Codex CLI which provider to use. Its value must match a provider id defined under `[model_providers.<id>]`.

`base_url` is the API endpoint where model requests are sent. For an OpenAI-compatible provider, it usually points to a `/v1` style endpoint.

`wire_api` tells Codex which protocol shape to use when talking to that provider. In the Codex configuration reference, `responses` is a supported provider protocol value.

## When this matters

- You are configuring a custom OpenAI-compatible provider
- Codex says the provider cannot be found or model requests fail
- You are not sure how `model_provider` differs from `model`
- You are putting BetterToken, OpenAI, or another provider in one `config.toml`
- You need to separate Base URL, API Key, and Model ID

## Field relationships

| Field | Purpose |
| --- | --- |
| `model_provider` | Selects the active provider id |
| `[model_providers.<id>]` | Defines one provider's detailed configuration |
| `name` | Display name for the provider |
| `base_url` | Root API endpoint |
| `wire_api` | Provider protocol, commonly `responses` |
| `model` | Default main model ID |
| `review_model` | Model used for code review flows such as `/review` |

## Recommended pattern

Keep the provider id consistent:

```toml
model_provider = "custom"
model = "gpt-5.5"

[model_providers.custom]
name = "BetterToken"
base_url = "{{openai-base-url}}"
env_key = "MODEL_PROVIDER_API_KEY"
wire_api = "responses"
requires_openai_auth = false
```

This means Codex uses the provider named `custom`, sends model requests to `{{openai-base-url}}`, and communicates through the Responses API shape.

Do not put the API Key directly in `config.toml`. Set it in the terminal that launches Codex:

```bash
export MODEL_PROVIDER_API_KEY="YOUR_API_KEY"
```

On Windows PowerShell:

```powershell
$env:MODEL_PROVIDER_API_KEY="YOUR_API_KEY"
```

## Verify the setup

1. Confirm that `model_provider = "custom"` exactly matches `[model_providers.custom]`.
2. Confirm that the Base URL is `{{openai-base-url}}`, including `/v1`.
3. Copy a current Model ID from the **GPT provider** in the <a href={"{{model-plaza-url}}"}>model plaza</a>.
4. Fully exit Codex and relaunch it from a new terminal where the environment variable is set.
5. Send a small code-explanation task and confirm that Codex returns a complete response.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| Provider not found | The provider id and configuration table do not match | Use `custom` in both places |
| Missing API Key at startup | The variable named by `env_key` is unavailable | Set `MODEL_PROVIDER_API_KEY`, then open a new terminal |
| `401` or `403` | Invalid API Key or mixed OpenAI authentication | Copy the Key again and set `requires_openai_auth = false` |
| `404` | The Base URL lacks `/v1` or points to an Anthropic endpoint | Use `{{openai-base-url}}` |
| Model not found | The value is a display name, retired model, or non-GPT model | Copy a current Model ID from the model plaza |
| Responses protocol error | `wire_api` is missing or incorrect | Set `wire_api = "responses"` |
